# Q-05 파일럿 리허설 시나리오

- 실행 예정: 2026-10-22, 파일럿: 2026-10-23. 현재 모든 TC는 **미실행**이다.
- 기준: D-34(범위 축소), D-35(주문 전체 취소), D-37(일시품절·삭제), D-39(기기·초기 데이터·결제 후 세션). D-39는 결정 기록 PR #35 기준이며 main 반영 여부를 실행 전에 확인한다.
- 브랜치: `feat/qa-q5`. 이 문서는 수동 리허설 절차이며 자동화 테스트 실행 결과가 아니다.
- 환경: B-11 머지·배포 완료 후 정주현이 제공한 Render 프론트 HTTPS 주소. 주소를 추측하지 않는다. API는 같은 주소의 `/api/v1`을 사용한다. 목 서버는 사용하지 않는다.
- 범위 제외: 레시피 입력·검증, 재고 차감·복원·경고 검증, 항목 단위 취소, 분석·발주 추천·SSE. 주문 전체 취소만 검증한다.

## 공통 준비·기록

1. `docs/ops/deploy-render.md`(B-11)와 `docs/ops/pilot-setup.md`(B-10)를 따른다. 문서·배포가 없으면 관련 TC를 차단으로 기록한다.
2. 정주현이 승인한 리허설용 테이블·메뉴·주문만 사용한다. 운영 DB 삭제·초기화, 마이그레이션 downgrade는 하지 않는다. 시나리오마다 새 주문을 만들고 이전 주문을 재사용하지 않는다.
3. 메뉴 32개·식재료 38개는 **B-19(PR #37) 머지 후** 비공개 파일로 공개 API를 통해 개발팀/QA가 일회성 입력한다. 사장에게 수동 입력을 요구하지 않는다. 파일·매입가·거래처·비밀번호·JWT·QR 토큰·접속 문자열은 커밋·채팅·캡처에서 제외한다.
4. 실제 배포 커밋, 프론트 주소(토큰 없는 기본 주소), 실행 시각, 브라우저, 기기·뷰포트, TC별 결과(통과/실패/부분 검증/차단/미실행), 기대와 실제, 증거 위치를 기록한다. HTTP 성공만으로 화면까지 통과시키지 않는다.
5. 계정은 B-10으로 준비한 사장·직원·주방 계정을 사용한다. 공개 문서에 고정 비밀번호를 두지 않는다. 테스트 데이터·주문 ID는 비밀값 없는 증거로만 기록한다.

## TC-50 배포·계정·초기 데이터 준비 (기존 SC-00)

- 전제: B-11 배포 완료, B-10 사용 가능. 초기 데이터 부분은 B-19 머지 필요.
- 절차: 프론트 주소의 `/api/v1/health`를 열고 세 역할로 각각 로그인한다. B-19 실행 결과와 사장 메뉴·식재료 목록의 실제 API 응답을 대조한다. 테이블별 QR을 준비한다.
- 기대 결과: health는 200과 `{"status":"ok"}`. 사장·직원·주방이 각 허용 화면에 진입한다. 초기 메뉴 32개·식재료 38개가 저장·조회되고 이름 중복이 없다. 집계 출력만으로 입력 성공을 판정하지 않는다. QR은 실제 Render 주소로 연결된다.
- 결과: 미실행.

## TC-51 QR 진입·실제 목록 (기존 SC-01·09)

- 전제: TC-50 완료, 서로 다른 두 테이블의 유효 QR.
- 절차: 휴대폰으로 QR을 스캔한다. 손님 메뉴판, 직원 대리 주문 목록, 사장 메뉴·식재료 목록을 실제 API 응답과 대조한다. 두 테이블을 각각 별도 브라우저 세션으로 연다.
- 기대 결과: 세션 발급 성공 후 판매 중 메뉴의 이름·가격이 표시된다. 목록 API의 `items`가 비어 있지 않은데 화면이 비면 실패다. 각 QR이 올바른 테이블에 연결되고 다른 테이블 주문이 섞이지 않는다. 토큰은 증거에서 가린다.
- 결과: 미실행.

## TC-52 손님 주문·중복 방지 (기존 SC-02)

- 전제: TC-51 완료, 판매 중 메뉴 A·B와 현재 가격 기록.
- 절차: A 수량 2와 B 수량 1을 담아 주문한다. 버튼 연속 클릭을 확인하고, 승인된 테스트 요청에서 동일 `Idempotency-Key`·동일 본문을 재전송한다.
- 기대 결과: `POST /orders` 성공 후 주문은 `received`, 항목은 `pending`. 수량과 합계는 표시 가격과 일치한다. 같은 키의 재요청은 같은 주문 ID를 반환하고 주문은 한 건만 생긴다. 화면에서 중복 클릭이 차단되어도 API 재시도 검증은 별도로 기록한다.
- 결과: 미실행.

## TC-53 주방 항목 처리·서빙 제한 (기존 SC-03)

- 전제: TC-52의 두 메뉴 항목, 주방·직원 로그인.
- 절차: 주방에서 A를 조리 시작·완료로 바꾸고 B는 대기로 둔다. 직원 화면의 서빙 버튼을 확인한다. B도 조리 시작·완료로 바꾼다.
- 기대 결과: 항목은 `pending → cooking → done`만 이동한다. 첫 조리 시작 시 주문은 `cooking`. 모든 항목이 `done`이 되기 전 서빙 버튼은 비활성이고 직접 served 요청도 409다. 모두 완료되어도 자동 서빙되지 않는다. 주방·직원은 다음 5초 폴링 응답 후 변경을 표시한다(네트워크 지연은 별도 기록).
- 결과: 미실행.

## TC-54 직원 서빙·결제·손님 세션 (기존 SC-04·05, D-39)

- 전제: TC-53의 모든 항목 완료 주문.
- 절차: 직원이 서빙 완료, 이후 카운터 결제 확인 후 결제 완료를 누른다. 손님 주문 내역을 갱신하고 같은 QR 세션으로 새 주문을 만든다.
- 기대 결과: 주문은 `served → paid`로 바뀌고 역전되지 않는다. 손님은 다음 10초 폴링 응답 후 상태 변경을 표시한다. 결제 완료 주문은 `/orders/mine`과 손님 내역에서 빠지지만 결제만으로 세션은 만료되지 않는다. 동일한 유효 세션으로 새 주문을 만들 수 있다. 직원 기본 진행 목록에는 결제 완료 주문이 남지 않는다.
- 결과: 미실행.

## TC-55 조리 전 주문 전체 취소 (기존 SC-06)

- 전제: 별도 신규 주문, 모든 항목 `pending`, 직원 로그인.
- 절차: 직원이 주문 전체를 취소하고 주방·직원·손님 화면을 갱신한다.
- 기대 결과: 주문 상태 변경 요청은 200, 주문은 `cancelled`. 주방 처리 대상과 직원 기본 진행 목록에서 제외된다. 항목 일부만 취소하는 버튼·요청은 사용하지 않는다. 다른 주문은 변경되지 않는다.
- 결과: 미실행.

## TC-56 조리 후 취소 권한 (기존 SC-07·08)

- 전제: 별도 주문에서 항목 하나를 주방 API로 `cooking`으로 변경한다.
- 절차: 직원 인증으로 주문 전체 취소 요청을 보낸 뒤 사장 인증으로 같은 주문 전체 취소를 요청한다. 사장 취소 화면이 없으면 API 검증과 화면 미검증을 분리한다.
- 기대 결과: 직원 요청은 403이고 주문은 `cooking` 그대로다. 사장 요청은 200이고 주문 전체가 `cancelled`가 된다. UI가 직원 동작을 숨겨도 API 권한 검증을 생략하지 않는다. 항목 상태에 `cancelled`를 새로 넣지 않는다(D-35).
- 결과: 미실행.

## TC-57 일시품절·판매 재개 (기존 SC-10, D-37)

- 전제: 승인된 테스트 메뉴와 품절 전 열린 손님·직원 장바구니.
- 절차: 사장이 메뉴를 일시품절(`PATCH /menus/{menu_id}`, `is_active=false`)로 바꾼다. 목록을 갱신하고 이전 장바구니로 주문을 시도한다. 이후 판매 다시 시작(`is_active=true`)을 누른다.
- 기대 결과: 사장 목록에는 '일시품절'로 남고 손님·직원 주문 선택에서는 숨겨진다. 직접/오래된 장바구니 주문은 409, 최상위 `code=MENU_UNAVAILABLE`과 문자열 `detail`을 반환하며 주문은 생성되지 않는다. 화면은 품절 안내 후 메뉴를 재조회한다. 판매 재개 시 같은 메뉴가 다시 선택·주문 가능하다. 일시품절은 삭제가 아니다.
- 결과: 미실행.

## TC-58 메뉴 삭제·과거 주문 보존 (D-37)

- 전제: 삭제가 승인된 별도 테스트 메뉴와 그 메뉴로 만든 과거 주문. 실제 판매 메뉴를 삭제하지 않는다.
- 절차: 삭제 확인창에서 먼저 취소하고 요청이 없는지 확인한다. 다시 삭제를 확인한 후 모든 목록과 과거 주문을 조회한다. 삭제 메뉴 ID로 주문·단건 조회·반복 삭제를 시도한다.
- 기대 결과: 취소 시 DELETE가 없다. 삭제 성공 시 사장·손님·직원 목록 모두에서 제외되고 복구 버튼은 없다. 과거 주문의 참조·메뉴 정보·금액은 보존된다. 삭제 메뉴 주문은 409 MENU_UNAVAILABLE, 단건 조회·반복 삭제는 404다. 이미 삭제된 메뉴 처리 시 사용자 안내와 목록 재조회가 동작한다.
- 결과: 미실행.

## TC-59 태블릿·휴대폰 현장 확인 (D-39)

- 전제: 직원·주방·사장 화면 로그인. 실제 태블릿·휴대폰과 767px·768px 경계 뷰포트를 준비한다.
- 절차: 세 역할 화면을 두 기기에서 각각 열어 목록·상태 버튼·입력·확인창·오류 안내를 조작한다. 가로/세로 전환과 긴 메뉴명·여러 주문을 확인한다. 두 테이블 주문의 번호가 주방·직원에서 일치하는지 대조한다.
- 기대 결과: 767px 이하는 휴대폰, 768px 이상은 태블릿 기준이며 필수 정보·버튼이 잘리거나 겹치지 않는다. 가로 스크롤 없이 핵심 흐름을 완료하고 스크롤·키보드 표시 중에도 저장·취소를 누를 수 있다. 주방·직원은 내부 table_id가 아닌 실제 테이블 번호를 표시한다.
- 후속 디자인 기준: 밝은 주방 테마, 10분 지연 표시, 휴대폰 레인 탭·태블릿 두 레인도 대조한다. 파일럿 후 예정 구현의 차이는 미구현으로 기록하며 기존 화면 통과로 대체하지 않는다. 리허설 필수 동작을 막는 문제는 민준에게 보고한다.
- 결과: 미실행. 에뮬레이션만 수행했으면 실제 기기 검증은 부분 검증으로 남긴다.

## 실행 순서·종료 조건

- TC-50 → TC-51 → TC-52 → TC-53 → TC-54 정상 흐름을 먼저 한다.
- TC-55·56은 각각 별도 주문, TC-57·58은 승인된 테스트 메뉴로 실행한다. TC-59는 정상 흐름과 메뉴 관리에 병행한다.
- 미머지·미배포 기능은 차단, 실행하지 않은 TC는 미실행으로 남긴다. 실패는 재현 단계·기대/실제·담당자·민준에게 보고한다. 기능 코드는 QA가 고치지 않는다.
- 리허설 종료 시 TC별 결과와 미해결 결함, 실제 기기 확인 여부, 배포 커밋을 민준에게 전달한다. 이 문서의 PR 완료는 Render 리허설 통과를 의미하지 않는다.
