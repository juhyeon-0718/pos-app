# 사장 관리 화면 명세 (U-01)

작성: 김지나 · 구현: 박지호(10/20) · 계약 기준: `docs/api/openapi.yaml` v0.2.0 · 토큰: `docs/design/DESIGN.md`
프로토타입: `owner/prototype/` (`menus.html`, `ingredients.html`, `recipe.html`). 브라우저로 열고 상단 "상태 보기" 바에서 상태를 전환한다. `?state=<키>`로 특정 상태를 바로 열 수 있다(§11). 더미 데이터만 쓴다.

## 0. 범위·원칙

### 용어집 (운영자 엑셀·F-06과 같은 쉬운 말)

| 계약 필드 | 화면 용어 | 예전 표기(쓰지 않음) |
|---|---|---|
| `safety_stock` | 최소로 남겨둘 양 | 안전 재고 |
| `lead_time_days` | 주문 후 도착까지 며칠 | 발주 리드타임, 리드타임 |
| `is_active=false` (메뉴) | 판매중지 | 비활성 |
| `is_active=false` (식재료) | 사용중지 | 비활성 |

표 머리글처럼 칸이 좁으면 `safety_stock`은 "최소로 남겨둘 양", `lead_time_days`는 "도착까지 며칠"로 줄여 쓴다. 식재료 "다시 사용" 버튼은 B-09 뒤(2차)다.

- 기기: 데스크톱 1024px 이상(사장 PC 기준). 1024px 미만은 표 가로 스크롤.
- 인증: `bearerAuth`(owner). 401이면 로그인 화면으로, 403이면 §1 문구.
- **파일럿 구현 범위:** 파일럿은 `/owner` 한 경로의 탭(메뉴 관리·식재료 관리)으로 구현한다. 라우터 도입과 아래 `/admin/...` 경로는 2차다. 화면 구조(모달·토스트·필터 칩·표)와 "더 보기"도 2차다.
- 화면 3개: 메뉴 관리(`/admin/menus`), 식재료 관리(`/admin/ingredients`), 레시피 편집(`/admin/menus/:menu_id/recipe`, **2차(D-34)**). 상단 바 탭 두 개(메뉴 관리·식재료 관리)로 이동한다. 상단 바와 표·모달 배치는 `features/owner` 안의 로컬 컴포넌트로 두고 다른 feature에서 가져다 쓰지 않는다(D-25). 버튼·입력창·모달·배지·배너·토스트는 공용 컴포넌트이며 §7에 정의한다.
- **삭제는 비활성화다.** `DELETE /menus/{menu_id}`(204)와 `DELETE /ingredients/{ingredient_id}`(200, 본문 Ingredient)는 계약상 `is_active=false`로 바꾸는 동작이다. 그래서 "삭제 후 복구 불가"라고 쓰지 않는다. 삭제하면 "판매중지/사용중지"로 바뀌고, 수정 또는 "다시 판매/다시 사용"으로 되돌릴 수 있다.
- 문구는 해요체. 메뉴명·식재료명은 평문(`textContent`)으로만 렌더링하고 길이는 말줄임(D-24).
- 상태는 기본·로딩·빈 상태·오류·비활성을 모두 정의한다. 비활성은 (a) 항목이 `is_active=false`인 경우, (b) 처리 중이라 버튼·입력이 잠긴 경우 두 가지다.

## 1. 공통 상태 규칙

| 상태 | 표현 | 문구 |
|---|---|---|
| 로딩(목록) | 표 틀 + 스켈레톤 5행, 상단에 스피너 + 글자. `aria-busy="true"`, "추가" 버튼 비활성 | "○○을(를) 불러오는 중이에요…" |
| 빈 상태 | 아이콘 + 제목 + 안내 + 주요 버튼 | 화면별 §2~4 |
| 조회 오류 | 오류 배너(`role="alert"`) + "다시 시도" 버튼. "추가" 버튼 비활성 | "○○ 목록을 불러오지 못했어요. 네트워크 상태를 확인하고 다시 시도해 주세요." |
| 저장 중 | 모달 입력·취소 비활성, 저장 버튼에 스피너 + "저장 중…". Esc로 닫히지 않음 | "저장 중…" |
| 저장 성공 | 모달 닫힘 → 목록 새로고침 → 토스트 4초 | "○○을(를) 저장했어요." |
| 저장 실패 409 | 모달 상단 오류 배너, 입력값 유지, 해당 입력에 `aria-invalid` | §2.3, §3.3 |
| 저장 실패 422 | 모달 상단 오류 배너, 입력값 유지 | "입력한 내용을 저장하지 못했어요. ○○을(를) 다시 확인해 주세요." |
| 401 | 로그인 화면으로 이동 | "로그인이 만료됐어요. 다시 로그인해 주세요." |
| 403 | 화면 전체 안내(편집 불가) | "사장 계정만 관리할 수 있어요." |
| 500·네트워크 | 오류 배너 | "서버에 문제가 생겼어요. 잠시 후 다시 시도해 주세요." |

- 오류는 토스트로 보내지 않는다(4초 후 사라져 놓치기 쉬움). 배너로 남기고 `role="alert"`. 성공 토스트만 `role="status"`.
- 입력 오류는 클라이언트에서 먼저 막는다. `Error`에 필드별 정보가 없어(`code`, `detail`뿐) 서버 422는 폼 전체 배너로만 보여준다.
- 서버 `Error.detail`이 있으면 배너 보조 문장 자리에 평문으로 표시한다(200자 제한). 없으면 위 고정 문구를 쓴다. `Error.code` 값이 확정되면 코드별로 나눈다(§9 요청 2).
- `POST /menus`, `POST /ingredients`에는 `Idempotency-Key` 헤더가 계약에 없다(`POST /orders`만 필수). 보내지 않고, 저장 중 저장 버튼을 비활성으로 두어 중복 클릭을 막는다.

## 2. 메뉴 관리 `/admin/menus` — `menus.html`

### 2.1 구성 (기본)
- 헤더: 제목 "메뉴 관리"(`--font-size-3xl`, bold), 보조 "손님 주문 화면에 나오는 메뉴와 가격을 관리해요.", 오른쪽 `+ 메뉴 추가`(primary).
- 필터 칩: `전체 n` / `판매중 n` / `판매중지 n`(`aria-pressed`). 내려받은 항목 안에서 클라이언트 필터. 오른쪽에 "n개 표시".
- 표(행 높이 56px): 메뉴명 | 카테고리 | 가격(오른쪽 정렬) | 상태 | 작업.
  - 메뉴명 `name`: 최대 260px, 말줄임, `title`로 전체 이름. 카테고리 `category`: 없으면 "미분류"(보조 색). 가격 `price`: `9,000원`.
  - 상태 `is_active`: `✓ 판매중`(success 배지) / `⊘ 판매중지`(보조 색 배지). 판매중지 행 글자는 보조 색.
  - 작업: 판매중 행 `수정` `레시피` `삭제`(삭제는 error 글자). 판매중지 행 `수정` `레시피` `다시 판매`. 각 버튼 `aria-label`에 메뉴명 포함("된장찌개 수정").
- `레시피`는 `/admin/menus/:menu_id/recipe`로 이동하며 메뉴명을 router state로 넘긴다(§9 요청 5).
- 페이지: `limit=50`. `has_more=true`면 표 아래 "더 보기"(`next_cursor`로 이어 붙이기). 이전 버튼은 없다(커서에 이전 방향이 없음). 불러오는 동안 "불러오는 중…"(비활성).

### 2.2 상태
- 로딩 / 조회 오류: §1. 빈 상태: 아이콘 + "아직 등록한 메뉴가 없어요" + "첫 메뉴를 추가하면 손님 주문 화면에 바로 나타나요." + `+ 메뉴 추가`. 필터 결과 없음: "조건에 맞는 메뉴가 없어요" + `전체 보기`.
- 비활성: 판매중지 행, 로딩·오류 중 `메뉴 추가` 비활성.
- "다시 판매": `PATCH /menus/{id}`에 `is_active=true`를 담아 바로 호출(확인창 없음). 토스트 "○○ 메뉴를 다시 판매해요."

### 2.3 추가/수정 모달 (`POST /menus`, `PATCH /menus/{menu_id}`, 본문 `MenuWrite`)
| 라벨 | 필드 | 입력 | 필수 | 검증(클라이언트) | 도움말·placeholder |
|---|---|---|---|---|---|
| 메뉴 이름 * | `name` | 텍스트 | O | 공백만 불가, 50자 이하(제안) | "예: 된장찌개" |
| 가격 * | `price` | 숫자, 뒤에 "원" | O | 0 이상 정수 | "예: 9000" |
| 카테고리 | `category` | 텍스트 + 기존 카테고리 제안(datalist) | X | - | "예: 찌개, 볶음, 밥" / "비워 두면 '미분류'로 보여요." |
| 판매 중 | `is_active` | 체크박스(기본 켜짐) | X | - | "(손님 주문 화면에 표시)" |

- 버튼 `취소`(secondary) `저장`(primary). 오류 상태로 저장하면 첫 오류 입력으로 포커스를 옮기고 문구는 입력 아래에 `⚠ 문장`으로 표시한다.
- 입력 오류 문구: "메뉴 이름을 입력해 주세요." / "메뉴 이름은 50자까지 입력할 수 있어요." / "가격을 입력해 주세요." / "가격은 0 이상의 정수로 입력해 주세요. (예: 9000)"
- 409: 배너 제목 "같은 이름의 메뉴가 이미 있어요." 보조 "다른 이름으로 바꿔서 저장해 주세요." 이름 입력에 오류 표시. (계약에 409 미정의 → §9 요청 2.)
- 422: 배너 제목 "입력한 내용을 저장하지 못했어요." 보조 "이름과 가격을 다시 확인해 주세요."
- 수정 모달은 현재 값을 채워 열고, `PATCH`에는 `name`·`price`를 항상 포함한 전체 본문을 보낸다(`MenuWrite` required, §9 요청 3).

### 2.4 삭제 확인 모달 (`DELETE /menus/{menu_id}`)
```
메뉴 삭제
"된장찌개" 메뉴를 삭제할까요?
삭제하면 "판매중지"로 바뀌고 손님 주문 화면에서 사라져요. 지난 주문 기록은 그대로 남고, 언제든 "다시 판매"로 되돌릴 수 있어요.
[취소]  [삭제]
```
- 열릴 때 포커스는 `취소`. 삭제는 danger. 처리 중 `삭제 중…`(스피너, 두 버튼 비활성). 성공(204) 토스트 "○○ 메뉴를 삭제했어요. (판매중지로 바뀌었어요)".
- 실패: 모달 유지 + 배너 "삭제하지 못했어요. 잠시 후 다시 시도해 주세요." + 버튼 `다시 시도`.

## 3. 식재료 관리 `/admin/ingredients` — `ingredients.html`

### 3.1 구성 (기본)
- 헤더: "식재료 관리", 보조 "레시피에 쓰는 식재료와 최소로 남겨둘 양, 단가를 관리해요.", `+ 식재료 추가`.
- **2차(D-34)** 경고 배너(재고 확인이 필요한 항목이 1개 이상일 때만): "재고 확인이 필요한 식재료가 n개 있어요." / "'부족' 또는 '재고 음수' 표시를 확인해 주세요." 대상은 사용중 항목 중 `current_stock < safety_stock` 또는 `current_stock < 0`.
- 필터 칩: `전체` / `사용중` / `사용중지`.
- 표: 식재료명 `name` | 단위 `unit` | 현재 재고 `current_stock` | 최소로 남겨둘 양 `safety_stock` | 도착까지 며칠 `lead_time_days` | 단가 `unit_price` | 상태 `is_active` | 작업.
  - 숫자 칸은 오른쪽 정렬. 재고 `12.5 kg`, 도착까지 며칠 `2일`, 단가 `9,800원/kg`. 값이 없으면(`safety_stock`·`lead_time_days`·`unit_price`는 계약상 선택) "-"(보조 색).
  - **2차(D-34)** 재고 부족: 현재 재고 아래에 배지 `⚠ 부족`(warning-text + warning-light, 주황 테두리) + 행 배경 `--color-warning-light`. `safety_stock`이 없으면 부족 판정을 하지 않는다.
  - **2차(D-34)** 음수 재고(D-07): 배지 `⚠ 재고 음수`(error). 사용중지 항목에는 부족·음수 배지를 붙이지 않는다.
  - 상태 배지 `✓ 사용중` / `⊘ 사용중지`. 작업: 사용중 `수정` `삭제`, 사용중지 `수정` `다시 사용`.
- 페이지·더 보기: §2.1과 같다(`limit=50`).

### 3.2 상태
- 로딩 / 조회 오류: §1. 빈 상태: "아직 등록한 식재료가 없어요" + "식재료를 추가한 뒤 메뉴 레시피에 연결하면, 주문이 들어올 때 재고가 자동으로 줄어요."(**2차(D-34)**, 파일럿에서는 이 문장을 뺀다) + `+ 식재료 추가`. 필터 결과 없음: 메뉴 화면과 같은 패턴.
- 비활성: 사용중지 행, 로딩·오류 중 `식재료 추가` 비활성.
- "다시 사용": `PATCH`에 `is_active=true`를 담아 바로 호출. 토스트 "○○ 식재료를 다시 사용해요."

### 3.3 추가/수정 모달 (`POST /ingredients`, `PATCH /ingredients/{ingredient_id}`, 본문 `IngredientWrite`)
| 라벨 | 필드 | 입력 | 필수 | 검증 | 도움말 |
|---|---|---|---|---|---|
| 식재료 이름 * | `name` | 텍스트 | O | 공백만 불가, 50자 이하(제안) | placeholder "예: 돼지고기(앞다리)" |
| 단위 * | `unit` | 텍스트 + 제안 목록(kg, g, L, mL, 개, 모, 단, 판, 봉, 병) | O | 공백만 불가 | "레시피 수량도 이 단위로 입력해요." |
| 현재 재고 | `current_stock` | **읽기 전용 줄**(수정 모달에만) | - | - | "재고 수량은 이 화면에서 바꿀 수 없어요." |
| 최소로 남겨둘 양 | `safety_stock` | 숫자, 뒤에 단위 | X | 0 이상 | "이 수량보다 적어지면 '부족'으로 표시해요." |
| 주문 후 도착까지 며칠 | `lead_time_days` | 숫자, 뒤에 "일" | X | 0 이상 정수 | "주문하고 받기까지 걸리는 일수예요." |
| 단가 | `unit_price` | 숫자, 뒤에 "원" | X | 0 이상 | "단위 1개당 가격이에요. 발주 비용 계산에 써요." |
| 사용 중 | `is_active` | 체크박스(기본 켜짐) | X | - | "(레시피에 넣을 수 있음)" |

- 선택 항목을 비우면 본문에서 그 필드를 보내지 않는다. 새 식재료의 `current_stock`은 계약상 입력할 수 없다(초기 재고는 §9 요청 8).
- 입력 오류 문구: "식재료 이름을 입력해 주세요." / "단위를 입력해 주세요. (예: kg, 개)" / "0 이상의 숫자로 입력해 주세요." / "0 이상의 정수(일)로 입력해 주세요."
- 409: 배너 "같은 이름의 식재료가 이미 있어요." + "다른 이름으로 바꿔서 저장해 주세요." 422: "입력한 내용을 저장하지 못했어요." + "이름, 단위와 숫자 항목을 다시 확인해 주세요."

### 3.4 삭제 확인 모달 (`DELETE /ingredients/{ingredient_id}`)
```
식재료 삭제
"양파" 식재료를 삭제할까요?
삭제하면 "사용중지"로 바뀌고 레시피 선택 목록과 발주 추천에서 빠져요. 재고 기록과 지난 분석 데이터는 그대로 남아요.
[취소]  [삭제]
```
- 409(레시피에서 참조 중, 계약에 정의됨): 같은 모달이 오류 상태로 바뀐다. 배너 제목 `"양파"은(는) 레시피에서 사용 중이라 삭제할 수 없어요.` 보조 "해당 메뉴의 레시피에서 먼저 이 식재료를 빼 주세요." 버튼은 `닫기` 하나. 사용 중인 메뉴 이름은 서버가 알려줄 때만 보조 문장에 붙인다(§9 요청 6).
- 그 밖 실패·처리 중·성공은 §2.4와 같다. 성공 토스트 "○○ 식재료를 삭제했어요. (사용중지로 바뀌었어요)".

## 4. 레시피 편집 `/admin/menus/:menu_id/recipe` — `recipe.html` — **2차(D-34)**

> 이 절 전체가 2차(D-34)다. 파일럿에서는 구현하지 않는다.

### 4.1 구성 (기본)
- 상단 `← 메뉴 목록으로`, 제목 "○○ 레시피", 보조 "손님이 이 메뉴를 1개 주문할 때 줄어드는 식재료와 양이에요."
- 행 목록(카드): 머리글 `식재료 | 메뉴 1개당 사용량 | 단위 | (빼기)`. 행마다 식재료 선택(`ingredient_id`), 사용량 입력(`qty_per_unit`), 단위(읽기 전용, 선택한 식재료의 `unit`), 빼기 버튼(`✕`, 44×44, `aria-label="○○ 빼기"`).
- 카드 아래 `+ 재료 추가`(secondary). 하단 오른쪽 `취소` `저장`(primary). 변경이 있으면 왼쪽에 `⚠ 저장하지 않은 변경이 있어요`.
- 식재료 선택 목록: `GET /ingredients`(limit=200, `has_more`면 이어서 요청)의 `is_active=true` 항목 + 이 행이 이미 쓰는 항목. 사용중지 항목은 이름 뒤에 "(사용중지)". 프로토타입은 `<select>`이며, 식재료가 많으면 검색 가능한 combobox로 구현해도 된다(키보드 조작·`aria` 유지).
- `PUT /menus/{menu_id}/recipe`는 배열 전체를 교체한다. 저장 본문은 `[{ingredient_id, qty_per_unit, unit}]`, `unit`은 선택한 식재료의 `unit` 값. 응답에 본문이 없으므로 성공 후 `GET`으로 다시 불러온다.
- 저장 버튼은 변경이 없으면 비활성. 변경 후 누르면 검증하고 오류가 있으면 첫 오류 입력에 포커스를 둔다.

### 4.2 검증 문구
- "식재료를 선택해 주세요." / "이미 추가한 식재료예요." / "0보다 큰 수량을 입력해 주세요."

### 4.3 상태
- 로딩: 스켈레톤 3행 + "레시피를 불러오는 중이에요…", `재료 추가`·`취소`·`저장` 비활성.
- 빈 상태: 아이콘 + "아직 레시피가 없어요" + "레시피를 등록하지 않으면 이 메뉴가 주문돼도 식재료 재고가 줄지 않아요." + `+ 재료 추가`(D-05: 재고는 레시피 기준으로 차감). 재료를 모두 지우고 저장하면 빈 배열을 보낸다(§9 요청 9).
- 조회 오류: 배너 "레시피를 불러오지 못했어요." + `다시 시도`.
- 사용중지 식재료 포함: 경고 배너 "사용중지된 식재료가 레시피에 있어요." / "식재료 관리에서 다시 사용으로 바꾸거나, 다른 식재료로 바꿔 주세요."
- 저장 중: 입력·선택·빼기·재료 추가·취소 비활성, 저장 버튼 "저장 중…". 성공 토스트 "○○ 레시피를 저장했어요."
- 저장 실패 409: 카드 상단 배너 "레시피를 저장하지 못했어요." / "식재료 정보가 바뀌었을 수 있어요. 목록을 새로 불러온 뒤 다시 확인해 주세요." 422: "입력한 내용을 저장하지 못했어요." / "식재료와 수량을 다시 확인해 주세요." 입력값은 유지한다. (PUT의 409·422는 계약 미정의, §9 요청 2.)
- 나가기 확인: 변경이 있을 때 `← 메뉴 목록으로` 또는 `취소`를 누르면 모달 "저장하지 않고 나갈까요?" / "저장하지 않은 변경 내용은 사라져요." `계속 편집`(포커스) `나가기`(danger). 새로고침·탭 닫기에도 `beforeunload` 확인을 건다.

## 9. 민준에게 요청할 계약 사항

계약 파일은 수정하지 않았다. 괄호 안은 확정 전까지 구현하는 방식이다.

1. **목록에 비활성 항목 포함 여부.** `GET /menus`, `GET /ingredients`가 사장 토큰에서 `is_active=false`도 내려주는지, 아니면 `is_active`/`include_inactive` 쿼리가 필요한지. (내려준다고 가정. 안 내려주면 "다시 판매/다시 사용"을 만들 수 없다.)
2. **오류 응답 정의.** `POST/PATCH /menus`, `POST/PATCH /ingredients`, `PUT /menus/{id}/recipe`의 409·422, 그리고 PATCH·PUT의 404가 응답에 선언돼 있지 않다. `Error.code` 값 목록(이름 중복, 레시피 참조 중, 검증 오류 등)도 필요하다. (고정 문구로 처리하고 `detail`을 보조 문장으로 표시.)
3. **PATCH 본문.** `PATCH /menus/{id}`·`/ingredients/{id}`가 `MenuWrite`·`IngredientWrite`를 그대로 써서 `name`·`price`(`name`·`unit`)가 필수다. "다시 판매"처럼 `is_active`만 바꿀 때도 전체 본문이 필요한지, 부분 수정 스키마를 둘지. (전체 본문 전송.)
4. **값 제약.** `name` 최대 길이, `price` 정수 여부·최솟값, `safety_stock`·`unit_price`·`lead_time_days` 최솟값, `qty_per_unit`>0, `category` 최대 길이와 빈 문자열 허용. (이름 50자, 가격 0 이상 정수, 나머지 0 이상, 수량 0 초과로 제한.)
5. **레시피 화면의 메뉴 이름.** `GET /menus/{menu_id}`가 없고 `GET .../recipe`도 메뉴 이름을 주지 않는다. 주소를 직접 열면 이름을 알 수 없다. (목록에서 넘겨받고, 없으면 `GET /menus`를 이어 불러 찾는다. 단건 조회 또는 응답에 `menu_name` 추가를 요청.)
6. **식재료 삭제 409 상세.** 어떤 메뉴가 쓰는지 알려주면 사장이 바로 고칠 수 있다. `detail`에 메뉴 이름을 넣거나 `used_in_menus: [{id, name}]`을 추가. (없으면 일반 문구.)
7. **`RecipeItem.unit`.** 서버가 식재료 `unit`으로 채우는지, 클라이언트가 보내야 하는지. 식재료 `unit`을 바꾸면 기존 레시피 항목의 `unit`이 따라 바뀌는지. (선택한 식재료의 `unit`을 보낸다.)
8. **초기 재고·재고 보정.** `IngredientWrite`에는 `current_stock`이 없고 새 식재료는 0에서 시작한다. 파일럿(D-30)에서 사장이 재고를 맞추려면 `POST /ingredients/{id}/movements`(restock/adjustment) 화면이 필요하다. U-01 범위 밖이라 설계하지 않았다. **범위에 넣을지(별도 U-xx로 분리할지) 정주현·민준 결정 요청.** 현재 화면은 재고를 읽기 전용으로 표시한다.
9. **레시피 비우기.** `PUT /menus/{id}/recipe`에 빈 배열을 보내면 레시피가 지워지는지, 같은 식재료가 중복된 배열은 422인지. (빈 배열 허용, 중복은 클라이언트에서 차단.)
10. **(선택)** 메뉴 목록에 `has_recipe`(또는 레시피 항목 수)가 있으면 "레시피 없음" 표시를 목록에 띄울 수 있다. 레시피가 없으면 재고가 차감되지 않아(D-05) 파일럿 중 누락을 막는 데 유용하다.

## 10. 구현 완료 조건 (박지호)

1. §1~4의 상태를 화면마다 모두 구현한다: 기본, 로딩, 빈 상태, 조회 오류, 저장 중, 저장 실패(409·422), 삭제 확인·삭제 실패, 사용중지 항목.
2. CSS 변수는 `DESIGN.md` 이름 그대로 `:root`에 둔다(`prototype/admin.css`의 `:root` 복사 가능). 색·크기 값을 직접 쓰지 않는다.
3. 문구는 이 명세 그대로 쓴다. 바꾸고 싶으면 김지나에게 먼저 알린다.
4. 필드 이름은 openapi.yaml과 같게 쓴다(§8). 계약 밖 필드를 요청·표시하지 않는다.
5. 메뉴명·식재료명은 평문으로만 렌더링한다(HTML 삽입 금지, D-24).
6. 접근성은 §5.4 항목을 지키고 터치 44px 이상, axe 위반 0건.
7. `frontend/src/features/owner/` 안에서만 구현하고 다른 feature에서 가져오지 않는다(D-25).

## 11. 프로토타입 상태 목록

경로는 `docs/design/owner/prototype/` 기준. 스크린샷은 저장소에 넣지 않았고, 아래 `?state=` 키로 같은 화면을 바로 열 수 있다. (예: `menus.html?state=m-409`)

| 파일 | `?state=` 키 |
|---|---|
| `menus.html` | `default`, `paged`(더 보기 있음), `paging`, `loading`, `empty`, `error`, `m-create`, `m-edit`, `m-invalid`, `m-saving`, `m-409`, `m-422`, `m-del`, `m-delbusy`, `m-delfail` |
| `ingredients.html` | 위와 같음 + `m-del409`(레시피 사용 중) |
| `recipe.html` | `default`, `dirty`, `inactive`, `loading`, `empty`, `error`, `invalid`, `saving`, `e409`, `e422`, `leave` |

프로토타입 동작은 시연용이다. 같은 이름으로 저장하면 409, 식재료 "양파" 삭제는 409, 입력 오류는 클라이언트 검증으로 나온다. 프로토타입 JS는 `file://`로 열어도 동작하도록 외부 파일을 받지 않는다.
