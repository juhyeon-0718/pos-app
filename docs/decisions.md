# 결정 기록 (Decision Log)

형식: 날짜 / 결정 / 이유. 새 결정은 아래에 추가한다. 번복 시 기존 항목은 지우지 않고 새 항목에 "D-xx 번복"을 적는다.
정주현 확인 대상(기술 스택, 외부 API 연동, 실제 발주·결제 등 되돌리기 어려운 결정)은 `확인: 정주현`을 표기한다.

---

## D-01 제품 범위
- 날짜: 2026-10-15 (기획 회의)
- 결정: 외부 POS 연동 없이, 지인 매장 1곳 전용 식당 운영 웹앱으로 만든다. 역할은 손님(테이블 QR, 비로그인)/직원/주방/사장. 앱 내 결제는 만들지 않고 카운터에서 결제한다.
- 이유: 실사용 매장이 1곳이고 POS 연동 비용 대비 효용이 낮다. 결제 연동은 리스크가 커 MVP에서 제외.
- 확인: 정주현

## D-02 발주는 추천까지만
- 날짜: 2026-10-15
- 결정: 발주는 추천까지만 하고 사장이 승인한다. 공급처로 자동 전송하지 않는다.
- 이유: 실제 발주는 되돌릴 수 없다. 예측 오류가 곧 비용 손실이 된다.
- 확인: 정주현

## D-03 인증
- 날짜: 2026-10-15
- 결정: 손님은 QR 스캔으로 테이블 세션 토큰을 받는다(4시간 경과 또는 결제 완료 시 만료, QR 재발급 시 즉시 무효). 직원·주방·사장은 JWT 로그인.
- 이유: 손님 로그인은 주문 이탈을 만든다. 토큰 만료·무효화로 QR 유출 시 악용을 제한.

## D-04 주문 상태
- 날짜: 2026-10-15
- 결정: 접수 → 조리중 → 서빙완료 → 결제완료. 어느 단계에서든 취소 가능, 이전 상태로 되돌리기는 금지.
- 이유: 단방향 상태로 주방/직원 화면 동기화와 감사 추적을 단순화.

## D-05 재고 모델
- 날짜: 2026-10-15
- 결정: 식재료 단위로 관리, 레시피 기준으로 주문 접수 시점에 차감. 모든 입출고는 `stock_movements` 원장에 기록하고 원장 합계를 현재 재고로 본다.
- 이유: 원장 방식이 정정·취소·감사에 안전하고, 발주 예측에 필요한 사용량 이력을 그대로 제공한다.

## D-06 주문 취소와 재고
- 날짜: 2026-10-15
- 결정: 조리 전 취소는 직원 가능, 재고 복원. 조리 후 취소는 사장만 가능, 재고는 복원하지 않고 폐기로 기록.
- 이유: 실제 식재료 소모를 반영하고, 조리 후 취소 남용을 권한으로 통제.

## D-07 재고 부족 처리
- 날짜: 2026-10-15
- 결정: 재고가 부족해도 주문을 막지 않는다. 음수 재고를 허용하고 경고한다. 품절은 메뉴 `is_active`로 처리.
- 이유: 재고 데이터가 실물과 어긋날 때 주문이 막히는 것이 더 큰 손해다.

## D-08 AI 역할 분담
- 날짜: 2026-10-15
- 결정: 발주 수량은 통계(이동평균, 요일별 패턴)로 계산한다. Claude API는 설명 문장만 생성하며 집계 데이터만 전송한다. API 키가 없어도 추천은 동작해야 한다.
- 이유: 수량 계산은 재현·검증 가능해야 한다. 원본 매출 데이터 외부 전송 최소화, 외부 장애 시에도 핵심 기능 유지.
- 확인: 정주현 (Claude API 사용). 키 발급 방식·모델은 미정.

## D-09 발주 추천 중복 방지
- 날짜: 2026-10-15
- 결정: 미처리 추천은 식재료당 1건(unique partial index). 반려 시 24시간 동안 같은 추천을 다시 띄우지 않으며 이 시간은 설정으로 변경 가능.
- 이유: 같은 추천 반복은 사장의 피로를 만든다. 쿨다운은 매장 운영에 맞게 조정 필요.

## D-10 기술 스택
- 날짜: 2026-10-15
- 결정: Backend FastAPI + PostgreSQL + Alembic / Frontend React + TS + Vite + Recharts + React Query + Zustand / 실시간 SSE.
- 이유: 팀 숙련도, 타입 안정성, 단방향 실시간(주방·손님 알림)에는 WebSocket보다 SSE가 단순.
- 확인: 정주현

## D-11 API 계약 우선
- 날짜: 2026-10-15
- 결정: `docs/api/openapi.yaml`을 먼저 확정(B0)하고 개발한다. 프론트는 Prism 목 서버로 선행 작업한다.
- 이유: 프론트·백엔드가 계약을 각자 만들면 머지 시점에 어긋난다.

## D-12 품질 기준
- 날짜: 2026-10-15
- 결정: pytest, Vitest, Playwright 사용. CI 실패 시 머지 차단. 테스트 데이터는 SEED=42로 고정.
- 이유: 재현 가능한 테스트와 자동 차단으로 리뷰 부담을 줄인다.

## D-13 브랜치·리뷰 규칙
- 날짜: 2026-10-15
- 결정: 브랜치는 `feat/<파트>-<작업ID>`(소문자). 파트는 `backend`/`frontend`/`qa`, 작업ID는 기획 회의 작업 목록 기준(B0~B3, F1~F3, Q1~Q2). 예: `feat/backend-b0`, `feat/frontend-f1`, `feat/qa-q1`. 모든 작업은 main으로 PR, 리뷰는 PR에 Approve/Request changes로 남기고 테크 리드가 머지한다. 작업 없는 임시 브랜치 `feat/back`은 삭제하고, `feat/front`(pos-app-front 워크트리)는 F1 시작 시 `feat/frontend-f1`로 이름을 바꾼다.
- 이유: 브랜치 이름만으로 담당 파트와 작업을 추적하고, 리뷰 기록을 PR에 남기기 위해.

## D-14 재고 부족 시 주문 응답
- 날짜: 2026-10-15
- 결정: `POST /orders`는 재고가 부족해도 201로 생성하고 응답에 `stock_warnings[]`(ingredient_id, 현재고, 필요량)를 포함한다. 직원·사장에게 SSE `stock.warning` 이벤트를 보낸다. 재고 부족을 이유로 한 생성 거부 응답은 계약에서 제거한다.
- 이유: D-07(주문을 막지 않음)과 일치시키고, 경고를 API 계층에서 검증 가능하게 하기 위해.

## D-15 주문 중복 생성 방지
- 날짜: 2026-10-15
- 결정: `POST /orders`에 `Idempotency-Key` 헤더(UUID)를 필수로 받는다. 같은 키로 재요청하면 기존 주문을 같은 응답으로 반환하고 재고는 다시 차감하지 않는다. 키는 `idempotency_keys` 테이블(유니크 제약)에 24시간 보관하며, 같은 키로 본문이 다르면 422를 반환한다.
- 이유: 버튼 중복 클릭이나 네트워크 재시도로 생기는 이중 주문과 이중 차감을 막는다. 시간창 방식은 경계가 모호해 테스트가 불안정하다.

## D-16 주문 상태와 항목 상태
- 날짜: 2026-10-15
- 결정: 주방은 항목 단위(`pending`→`cooking`→`done`)로 처리한다. 주문 상태는 서비스 레이어가 같은 트랜잭션 안에서 자동으로 계산한다(조리중 항목이 하나라도 있으면 주문은 `cooking`). `served`와 `paid`는 직원이 주문 단위로 변경한다. DB 트리거는 사용하지 않는다.
- 이유: 실제 주방 작업 흐름을 반영하면서 D-04의 단방향 주문 상태를 유지한다. 서비스 레이어에서 처리해야 테스트하기 쉽다.

## D-17 손님 주문 상태 갱신
- 날짜: 2026-10-15
- 결정: MVP에서는 손님 화면이 `GET /orders/mine`을 10초 간격으로 폴링한다. 손님용 SSE는 MVP 이후 검토한다.
- 이유: SSE 연결 유지와 재연결 처리, 그 테스트 비용이 MVP 범위를 넘는다. 손님 쪽 지연은 수용할 수 있는 수준이다.

## D-18 상태 enum 표기
- 날짜: 2026-10-15
- 결정: API의 상태 값은 영문 코드로 쓴다. 주문: `received`/`cooking`/`served`/`paid`/`cancelled`. 항목: `pending`/`cooking`/`done`. 한글 라벨은 프론트 매핑 테이블에서 관리한다.
- 이유: 코드·테스트 가독성을 높이고 인코딩 문제를 없앤다. 표시 문구는 API 변경 없이 바꿀 수 있다.

## D-19 조리 후 취소의 재고 원장 기록
- 날짜: 2026-10-15
- 결정: 조리 후 취소 시 `stock_movements`에 `cancel_restore`(+수량)와 `disposal`(-수량)을 한 쌍으로 같은 트랜잭션에 기록한다. 순 재고 변화는 0이다. 조리 전 취소는 `cancel_restore`(+수량)만 기록한다.
- 이유: D-05(원장 합계 = 현재 재고)를 지키면서, 폐기량을 판매 사용량과 분리해 집계할 수 있다. `disposal`만 단독으로 기록하면 재고가 이중으로 차감된다.

## D-20 origin 접근 불가 시 임시 머지 절차
- 날짜: 2026-10-15
- 결정: GitHub 인증이 복구될 때까지 테크 리드가 로컬에서 브랜치를 검증한 뒤 `--no-ff`로 로컬 main에 머지한다. 리뷰 기록은 Slack 스레드에 남긴다. 인증이 복구되면 main과 작업 브랜치를 push하고, 이후 작업부터 PR 절차(D-13)로 돌아간다.
- 이유: 계약(B0) 머지가 모든 작업의 선행 조건이라 인증 문제로 전체 일정이 멈추는 것을 막기 위해서다. 로컬 머지는 push 전까지 되돌릴 수 있다.

## D-21 개발·테스트 DB 환경
- 날짜: 2026-10-16
- 결정: 호스트에 PostgreSQL 16을 직접 설치하고 `pos_app_dev`(개발)와 `pos_app_test`(pytest) DB를 둔다. pytest는 PostgreSQL로만 돌리고 SQLite 기본값은 제거한다. 접속 정보는 `DATABASE_URL` 환경변수로 받고 `.env`는 커밋하지 않는다(`.env.example`만 커밋).
- 이유: D-09 partial unique index와 동시 차감 시 `SELECT ... FOR UPDATE` 행 잠금(TC-01)은 SQLite에서 검증할 수 없어 false positive가 생긴다. D-10 스택을 바꾸는 결정이 아니고, Docker보다 설치 요건(WSL2, 관리자 권한)이 적다.
- 확인: 호스트 설치 권한은 정주현 확인 대기.

## D-22 B1 인증 범위
- 날짜: 2026-10-16
- 결정: B1은 stub 인증(`X-Role` 헤더)을 유지하고 `ENV`가 `dev` 또는 `test`일 때만 켠다. 그 외 환경에서는 앱 시작을 실패시킨다. JWT(`POST /auth/login`)는 B2에서 구현하고, stub 삭제를 B2 완료 조건에 넣는다. 인증 스킴(`securitySchemes`)이 바뀌면 프론트에 먼저 알린다.
- 이유: B1 범위를 늘리면 일정이 밀린다. TC-03~TC-05 권한 검증은 stub으로도 가능하고, 프론트는 Prism 목 서버로 작업해 영향이 없다.
